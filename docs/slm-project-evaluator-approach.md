# Fine-Tuning a Small Language Model for Project Idea Evaluation

## 1. Problem Definition

Given a free-text project description (e.g. "An app that helps freelancers track unpaid invoices and auto-send reminders"), the model should output a structured evaluation across multiple business-viability dimensions, each scored on a 1–10 scale with a brief justification.

### Output Dimensions

| Dimension | What It Captures |
|---|---|
| **Pain Severity** | How painful is the problem the project solves? (1 = mild inconvenience, 10 = critical blocker) |
| **Pain Frequency** | How often does the target user encounter this problem? (1 = rarely, 10 = daily/constant) |
| **Existing Alternatives** | How well do current solutions address the problem? (1 = saturated/well-solved, 10 = no good alternatives) |
| **Willingness to Pay** | How likely are users to pay for this solution? (1 = expects free, 10 = happily pays premium) |
| **Market Size** | How large is the potential addressable market? (1 = tiny niche, 10 = massive global market) |
| **Scalability** | How easily can the project scale with low marginal cost? (1 = hard to scale, 10 = near-zero marginal cost) |
| **Profitability Potential** | Overall revenue/margin potential considering unit economics? (1 = low, 10 = high) |
| **Defensibility** | How hard is it for competitors to replicate? (1 = trivially copyable, 10 = strong moat) |
| **Time to Value** | How quickly can users see value after first use? (1 = months, 10 = instant) |
| **Founder-Market Fit Requirement** | How much domain expertise is needed to execute? (1 = anyone can build, 10 = deep domain required) |

The model should also produce an **Overall Score** (weighted average) and a short **Summary** paragraph.

## 2. Model Selection

### Why Small Language Models?

We need a model that:
- Runs on consumer hardware (8–16 GB RAM, optionally a modest GPU)
- Produces structured, consistent output
- Can be fine-tuned affordably on a single GPU or even CPU with QLoRA

### Candidate Models

| Model | Parameters | RAM (Quantized) | Why Consider |
|---|---|---|---|
| **Qwen2.5-3B-Instruct** | 3B | ~2–3 GB (Q4) | Strong instruction-following at small size, multilingual |
| **Phi-3.5-mini-instruct** | 3.8B | ~2.5 GB (Q4) | Microsoft's reasoning-optimized small model, excellent structured output |
| **Llama-3.2-3B-Instruct** | 3.2B | ~2–3 GB (Q4) | Meta's latest small model, good general reasoning |
| **Gemma-2-2B-it** | 2.6B | ~1.8 GB (Q4) | Google's efficient small model, solid instruction following |
| **SmolLM2-1.7B-Instruct** | 1.7B | ~1.2 GB (Q4) | HuggingFace's tiny model, runs on almost anything |

### Recommended Starting Point

**Qwen2.5-3B-Instruct** — best balance of size, structured output quality, and multilingual support. Falls back gracefully on CPU-only machines.

**Phi-3.5-mini-instruct** — if you want slightly better reasoning at a small cost in size.

## 3. Fine-Tuning Approaches

### 3.1 Approach A: Supervised Fine-Tuning with Synthetic Data (Recommended Start)

**Idea:** Use a large teacher model (GPT-4o, Claude, etc.) to generate high-quality evaluation examples, then distill into the SLM.

**Pipeline:**
```
[Collect/Generate Project Descriptions]
        ↓
[Teacher Model generates structured evaluations]
        ↓
[Quality filter + human review of a sample]
        ↓
[Format as instruction-tuning pairs]
        ↓
[Fine-tune SLM with QLoRA / LoRA]
        ↓
[Evaluate on held-out set]
```

**Data Generation Strategy:**
1. Curate 200–500 diverse project descriptions from:
   - Product Hunt launches
   - YC company descriptions
   - Indie Hackers projects
   - Synthetic variations generated by an LLM
2. For each, prompt a teacher model to produce the structured evaluation
3. Human-review ~10–20% for quality calibration
4. Target: 1,000–5,000 training examples (augmented with paraphrases)

**Training Format (Chat Template):**
```json
{
  "messages": [
    {
      "role": "system",
      "content": "You are a startup and project evaluator. Given a project description, evaluate it across 10 business-viability dimensions, each scored 1-10 with a brief justification. Output valid JSON."
    },
    {
      "role": "user",
      "content": "Evaluate this project: An app that helps freelancers track unpaid invoices and auto-send payment reminders via email and SMS."
    },
    {
      "role": "assistant",
      "content": "{\"pain_severity\": {\"score\": 8, \"reason\": \"Unpaid invoices directly impact freelancer income and cash flow\"}, ...}"
    }
  ]
}
```

**Training Configuration:**
- Method: QLoRA (4-bit quantized base + LoRA adapters)
- LoRA rank: 16–64
- Learning rate: 1e-4 to 2e-4
- Epochs: 2–4
- Batch size: 4–8 (with gradient accumulation)
- Hardware: Single GPU with 8+ GB VRAM, or CPU with patience

**Estimated Cost/Time:**
- Data generation: $5–20 in API calls
- Training: 1–4 hours on a single T4/RTX 3060, or 8–24 hours on CPU
- Total: Under $50 if using cloud GPU

---

### 3.2 Approach B: Few-Shot Prompting + Constrained Decoding (No Fine-Tuning)

**Idea:** Skip fine-tuning entirely. Use the base instruct model with a carefully crafted system prompt and few-shot examples, combined with structured output enforcement.

**Pros:**
- Zero training cost
- Instant iteration on prompt changes
- Good baseline to compare fine-tuned model against

**Cons:**
- Less consistent output quality
- Uses more context window per request (few-shot examples are verbose)
- Harder to enforce exact schema compliance

**When to use:** As your v0 baseline before investing in fine-tuning.

---

### 3.3 Approach C: DPO/ORPO Alignment After SFT

**Idea:** After initial SFT (Approach A), further align the model using preference data.

**Pipeline:**
```
[Fine-tuned model generates 2-3 evaluations per project]
        ↓
[Human annotators rank which evaluation is best]
        ↓
[Train with DPO (Direct Preference Optimization)]
```

**When to use:** After Approach A, if you notice the model produces technically valid but qualitatively poor evaluations (e.g., scores are reasonable but justifications are shallow).

**Data needed:** 500–1,000 preference pairs.

---

### 3.4 Approach D: Reward Model + Iterative Self-Improvement

**Idea:** Train a small reward model that scores evaluation quality, then use it to filter/rank model outputs during iterative training.

**When to use:** At scale, when you have thousands of users providing implicit feedback (e.g., "this evaluation was helpful" signals).

## 4. Data Strategy

### 4.1 Data Sources for Project Descriptions

| Source | Volume | Quality | Notes |
|---|---|---|---|
| Product Hunt | High | Good | Real launched products with descriptions |
| YC Company Directory | Medium | High | Vetted startup descriptions |
| Indie Hackers | Medium | Good | Solo/small team projects |
| Kickstarter/Indiegogo | High | Mixed | Crowdfunded project pitches |
| Synthetic (LLM-generated) | Unlimited | Variable | Augment with diverse industries/niches |
| Reddit r/startups, r/SideProject | Medium | Mixed | Raw, unpolished ideas |

### 4.2 Data Quality Checklist

- [ ] Descriptions span diverse industries (SaaS, hardware, marketplace, content, etc.)
- [ ] Mix of good ideas (should score high) and bad ideas (should score low)
- [ ] Include edge cases: vague descriptions, overly ambitious, niche markets
- [ ] Teacher model outputs are valid JSON and scores are calibrated
- [ ] Human review confirms scores feel reasonable (±1 point tolerance)

### 4.3 Data Augmentation

- Paraphrase project descriptions (different wording, same idea)
- Vary description length (one-liner vs. detailed paragraph)
- Add noise: typos, informal language, non-English mixed in
- Generate "adversarial" descriptions designed to trick the model

## 5. Evaluation Strategy

### 5.1 Automated Metrics

| Metric | What It Measures |
|---|---|
| JSON validity rate | % of outputs that parse as valid JSON |
| Schema compliance | % of outputs with all required fields |
| Score distribution | Are scores well-distributed or clustered? |
| Score correlation with teacher | Pearson/Spearman correlation per dimension |
| MAE per dimension | Mean absolute error vs. teacher scores |

### 5.2 Human Evaluation

- Blind comparison: fine-tuned SLM vs. teacher model vs. few-shot baseline
- Evaluators rate: accuracy, helpfulness, consistency
- Inter-annotator agreement on a subset

### 5.3 Behavioral Tests

- Same project, different wording → scores should be similar
- Clearly terrible idea → all scores should be low
- Clearly great idea → scores should be high
- Nonsense input → model should indicate it cannot evaluate

## 6. Deployment Considerations

### 6.1 Inference Options

| Method | Speed | Setup Complexity | Best For |
|---|---|---|---|
| **llama.cpp (GGUF)** | Fast | Low | Local CLI/API, any hardware |
| **Ollama** | Fast | Very Low | Quick local deployment |
| **vLLM** | Very Fast | Medium | GPU server deployment |
| **Transformers + bitsandbytes** | Moderate | Low | Python-native, prototyping |
| **ONNX Runtime** | Fast | Medium | Edge/mobile deployment |

### 6.2 Quantization

For consumer devices, use GGUF Q4_K_M quantization:
- ~50% size reduction vs. FP16
- Minimal quality loss for this task
- Runs on CPU with acceptable latency (2–10 seconds per evaluation)

### 6.3 Output Parsing

Always wrap inference with a JSON parser + retry logic:
```
[Generate] → [Parse JSON] → [Validate Schema] → [Return or Retry]
```

## 8. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Model hallucinates market data | Train it to reason from description only, not claim factual market stats |
| Score clustering (everything gets 5–7) | Include polarized examples in training data |
| JSON output breaks | Constrained decoding + retry logic |
| Overfitting to teacher model biases | Diversify teacher prompts, add human corrections |
| Model too slow on CPU | Use smaller model (SmolLM2-1.7B) or aggressive quantization |
